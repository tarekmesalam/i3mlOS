# Agent-Native Primitives: What an OS Must Provide for Agents as First-Class Citizens

**Framing.** A classical OS virtualizes CPU, memory, and I/O for *processes*. An agent-native OS must virtualize a new resource set — model inference, context, tools, and trust — for *goals*. The design rule: everything an agent does must pass through kernel-mediated primitives, never ad-hoc framework code. Nobody has built this whole stack; every layer has a partial precedent.

## 1. Agent lifecycle & scheduling (replaces processes)
A process is code + address space. An agent is **goal + context + capability set + budget**, and it is *durable*: it suspends mid-task for hours (waiting on a human, a webhook, a cheaper model tier) and must resume with intact state. The scheduler primitive isn't a run-queue; it's **durable execution** — checkpoint/replay of agent steps. Exists today: Temporal/Restate-style durable workflows, LangGraph checkpointers, Letta's stateful agent runtime. Must be invented: a kernel-level "agent control block" (goal, lineage, budget, capability handles) with `spawn/suspend/resume/kill/fork` syscalls, and scheduling by *deadline and budget* rather than CPU timeslice.

## 2. Persistent memory as a filesystem-level service
Context windows are RAM; agent memory needs a disk. Letta (ex-MemGPT, UC Berkeley) already models this explicitly as OS-style tiers: core memory (in-context, RAM-like), archival memory (searchable store, disk-like), recall memory. Mem0/Zep offer bolt-on memory layers. What the OS must invent: a **system-wide memory service** — a VFS-like namespace (`/memory/user/preferences`, `/memory/agent/<id>/episodic`) with ACLs, so memory is shared across agents by permission, not siloed per app, and users can inspect/edit/delete what the system "knows."

## 3. Capability-based permissions & sandboxing
The right model exists in research OSes: **capabilities** (unforgeable, delegable, revocable handles) as in seL4 and Fuchsia's Zircon — not Unix's ambient user-based authority. An agent should hold `read:~/Projects/*`, `send-email:draft-only`, each attenuable when delegated to sub-agents, all revocable mid-task. For execution isolation the tech is mature: **Firecracker microVMs** (~125 ms boot; powers AWS Lambda and agent-sandbox platforms like E2B/Daytona; AWS shipped "Lambda MicroVMs" for AI-generated code in June 2026), gVisor (user-space kernel, ~10–15% overhead), bubblewrap/Landlock (lightweight, kernel-shared). 2026 consensus: microVMs for untrusted/generated code; containers alone are insufficient. Windows 11's Build 2026 "agent workspace" (separate agent accounts, scoped desktops) validates the direction. Must be invented: the capability *policy layer* mapping natural-language intent to least-privilege grants.

## 4. Tool access — MCP is the syscall layer (mostly)
MCP has won the interface war: ~97M monthly SDK downloads by March 2026, 9,600+ registry servers, ~28% Fortune-500 adoption, active spec evolution (July 2026 release candidate). It is the right *ABI*: typed tool discovery + invocation. But a syscall layer implies **kernel mediation** — MCP today is a library the agent process links, so a compromised agent calls tools directly. The OS must invent an **MCP broker**: every tool call traverses a trusted process that enforces capabilities, logs, meters cost, and injects approval gates — analogous to Flatpak portals or Android Binder, with MCP as the wire format.

## 5. Inter-agent communication
**A2A** (Google → Linux Foundation, June 2025; 150+ member orgs, v1.0.1 May 2026, adopted across Google/Microsoft/AWS) is the emerging cross-vendor protocol; agent cards ≈ service discovery. On-device, the OS needs cheaper IPC: shared memory-blocks (Letta supports this), typed message passing, and — uninvented — **trust propagation**: when agent A tasks agent B, B runs under an attenuated subset of A's capabilities and budget (cgroup-style inheritance).

## 6. Human-in-the-loop as a kernel concept
Today approval is per-app UX (Claude Code permission prompts, MCP's elicitation feature, Copilot Actions confirmations). Kernel-native means: tool calls carry **reversibility/risk classes**; irreversible actions (send, pay, delete) trap to a system-owned approval surface no agent can render or spoof — like a secure-attention-key (Ctrl-Alt-Del) for consent. Approvals are policies ("auto-approve reads, queue sends for batch review"), persisted and auditable. This barely exists anywhere and is a genuine invention opportunity.

## 7. Observability & audit
**OpenTelemetry GenAI semantic conventions** (spans for LLM calls, agent steps, tool invocations; stabilizing through 2026, CNCF-graduated project, supported by Datadog/New Relic/Honeycomb) provide the schema. The OS addition: an **append-only system journal** — every tool call, capability grant, approval, and token spend, recorded by the broker (not self-reported by agents), queryable as "what did my computer do while I slept?" This is the trust foundation everything else rests on.

## 8. Local vs cloud model routing
Inference is a device like GPU: agents request *qualities* ("fast/cheap/private" vs "frontier"), not models. Precedents: Apple's Foundation Models framework (on-device ~3B + Private Cloud Compute), Windows Foundry Local, Ollama/llama.cpp; routing via LiteLLM/OpenRouter/RouteLLM. Must be invented: kernel-enforced **data-residency policy** — capability-tagged data (e.g., `/memory/health/*`) physically cannot route to cloud endpoints.

## 9. Token/cost budgeting as a first-class resource
Tokens are the new CPU-seconds. LiteLLM-style per-key budgets exist, but only as gateway config. The OS needs **cost-groups** (cgroups for spend): hierarchical budgets per agent tree, inherited on spawn, with scheduler integration — degrade to a local model when a budget nears exhaustion, suspend rather than overspend, expose burn-rate in the system monitor next to CPU/RAM.

## Honest bottom line
Reusable today: MCP, A2A, Firecracker/gVisor, OTel GenAI, Letta-style memory, LiteLLM routing. To invent: the *kernel itself* — durable agent scheduler, capability broker mediating MCP, system memory VFS, spoof-proof approval surface, unified journal, cost-groups. That broker + journal + capability model is the defensible core of i3mlOS; everything else can be assembled from the ecosystem. Microsoft is bolting this onto Windows; the open question i3mlOS answers is what it looks like built agent-first.
